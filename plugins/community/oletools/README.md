# oletools

Анализ макросов офисного документа (decalage2/oletools, `olevba`): какие
модули VBA/XLM нашлись, автоисполняемые вставки, подозрительные вызовы и IOCs.
Исходный код макросов в отчёт не попадает (запускаем с `-a`, и поле `code`
не копируется).

## Установка донора

Пин объявлен в манифесте (`runtime.requires`) и в `requirements.lock`:

```
pip install oletools==0.60.2
```

По умолчанию вызывается `python3 -m oletools.olevba`, а не console-script
`olevba`: pip кладёт скрипты в каталог `Scripts` (на Windows), а он часто не в
PATH — и донор оказывается установленным и «не найденным» одновременно. Путь к
донору можно переопределить env `OLETOOLS_BIN` (имя из PATH, полный путь или
`.py`-мок).

## Путь в argv и subfilename

`olevba` пишет в `subfilename` ровно то, что получил в argv. Поэтому донор
запускается с **cwd = каталог документа** и получает в argv только имя файла:
с абсолютным путём в это поле попал бы путь машины (на Windows — с обратными
слэшами и кириллицей, то есть значение, которое нельзя ни сравнить в тесте, ни
перенести на другую машину). Полный путь и так дан выше, в порту `file`.

## Порты

| порт | тип | источник |
|---|---|---|
| `file` | string | строка оператора |
| `file_type` | string | `type` донора: `OLE`, `OpenXML`, `Text`, `XML`, `MHTML`, `RTF`, `SLK` |
| `macros` | array | `[{vba_filename, subfilename, ole_stream}]` |
| `findings` | array | `[{type, keyword, description}]` — строки словарей донора (`AutoExec`, `Suspicious`, `IOC`) |
| `count` | number | сколько находок |
| `tool_version` | string | версия `olevba` из `MetaInformation.version` |

`tool_version` обязателен: без него «макросов нет» неотличимо от «эта версия
olevba не знает такой формат». Пустой `file_type` означает «эта версия не назвала
тип», а не «тип неизвестен обёртке».

Из `MetaInformation` берётся ровно одно поле — `version`. `python_version` — это
свойство машины, а не документа, `url` — рекламная строка oletools; ни то, ни
другое наружу не идёт.

## Чего в выводе нет и почему

- `code` — исходник макроса. Плагин разбирает документ, а не публикует его
  содержимое: код ушёл бы в контекст рана и дальше в отчёты, где он
  неотличим от данных. `-a` у донора печать кода гасит, но поле не копируется
  всё равно — по списку разрешённых имён.
- `container` — путь контейнера, в котором лежит вложенный OLE-файл
  (например `word/embeddings/oleObject1.bin`): внутренний идентификатор структуры
  документа.
- `do_deobfuscate`, `show_pcode`, `code_deobfuscated` — настройки запуска и
  результат деобфускации, а не находки. Деобфускация не включается: она меняет
  текст макроса, и в выводе оказался бы уже не тот код, который в файле.

## Фикстуры

`fixtures/` собраны `fixtures/make_ole.py` — это **настоящие** CFB-контейнеры
([MS-CFB]) с VBA-проектом ([MS-OVBA]), собранные с нуля. Свой файл вместо
чужого: в дистрибутивах pip oletools документа с макросом нет, а качать бинарь
из интернета ради фикстуры нельзя.

- `macro.doc` — OLE с VBA-проектом: `PROJECT`, `VBA/_VBA_PROJECT`, `VBA/dir`,
  `VBA/Module1`. Настоящий olevba на нём находит модуль `Module1.bas` и четыре
  находки: `AutoExec/AutoOpen` и `Suspicious` на `Shell`, `vbHide`, `powershell`.
  Исходник макроса напечатан в `VBA_SOURCE` в сборщике.
- `nomacros.doc` — OLE-документ **без** макросов. Нужен, чтобы «макросов нет»
  было проверено живым донором: ноль находок — это результат, а не ошибка.
- `truncated.doc` — первые 1024 байта `macro.doc`: каталог обещает секторы за
  концом файла, и настоящий olevba на этом падает (exit 8). Это проверяемая
  ветка отказа, а не выдуманная.

Плагин для аудита собственных или явно полученных для проверки документов.
