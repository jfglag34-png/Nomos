# Webhook idempotency (актуальный контракт с постоянной очередью)

POST /trigger/<job> требует Bearer-токен и Idempotency-Key: 1..128 ASCII-символов без пробелов/управляющих символов. Новый UUID на новое намерение; прежний ключ на сетевой повтор. Область ключа — один job. Тело запроса не исполняется.

```bash
curl -X POST \
 -H 'Authorization: Bearer YOUR_TOKEN' \
 -H 'Idempotency-Key: parser-batch-001' \
 http://127.0.0.1:8770/trigger/parser-1
```

- 202: задание устойчиво записано в очередь; выполнение ещё не завершено.
- 200 + Idempotency-Replayed: true: тот же ключ, без нового задания; текущий сохранённый status.
- 429 + Retry-After: 5: очередь заполнена; повторить тот же ключ позже.
- 400: неверный/отсутствующий ключ.
- 503: хранилище/завершение демона; повторять только тот же ключ и проверить health.
- 401/404: авторизация/неизвестный job.

Возвращается task_id (он же trigger_id). GET /tasks/<task_id> с Bearer показывает сохранённый статус. Задание и claim сохраняются одним снимком с fsync до 202. 64 конкурентных запроса с одинаковым ключом создают одно задание. Повтор после рестарта не дублирует его.

Pending переживает рестарт и продолжает ожидание; running становится interrupted и автоматически не повторяется. Это не exactly-once внешних эффектов: плагин мог совершить действие до аварии. Старые claims из .trigger-claims также блокируют повтор, но дают прежнюю квитанцию без текущего статуса нового задания.

Все ограничения хранения, восстановления и outbox: [fleet-reliability.md](fleet-reliability.md). Не удаляйте хранилище дедупликации при чистке логов. История пока без TTL/compaction; нужны контроль диска и резервное копирование.
