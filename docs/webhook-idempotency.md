# Раунд 1: защита webhook от повторного исполнения

## Контракт

`POST /trigger/<job>` теперь **требует** заголовок `Idempotency-Key` (breaking change для старых клиентов). Используйте новый UUID на каждое намерение запустить цепочку; при сетевом повторе отправляйте прежний ключ.

```bash
curl -X POST \
  -H 'Authorization: Bearer YOUR_TOKEN' \
  -H 'Idempotency-Key: parser-batch-2026-10-19-001' \
  http://127.0.0.1:8770/trigger/parser-1
```

- 202: сохранена квитанция, запуск принят (не подтверждение выполнения).
- 200 + `Idempotency-Replayed: true`: этот ключ для этой цепочки уже зарегистрирован, **нового запуска нет**. Возвращается тот же trigger_id, статус claimed, execution_status=not_reported. Это не подтверждение успеха исходного прогона.
- 400: ключ отсутствует/невалиден. Ключ: 1..128 ASCII-символов без пробелов/управляющих символов.
- 409: цепочка занята, нет слота или демон завершается. Ключ освобождён; можно повторить **тот же** ключ позже.
- 503: проблема хранилища/повреждённая квитанция. Fail-closed: не запускать автоматически с новым ключом, сначала проверить журнал и состояние.
- 401/404: прежние проверки авторизации и существования цепочки.

Один ключ независим для разных job. Тело запроса не используется: только заданная оператором конфигурация цепочки. Если конфигурация изменилась, старый ключ всё равно не запустит job повторно — нужен новый ключ для нового намерения.

## Как обеспечивается

Ключи не хранятся в открытом виде: имя квитанции — SHA-256(job + разделитель + key). Каталог: `<runs_dir>/.trigger-claims`, права 0700, файлы 0600. Мьютекс сериализует проверку/создание/приём запуска. Создание O_EXCL; содержимое и каталог синхронизируются fsync **до** старта процесса. Сам fleet защищён от второй копии на том же runs_dir через flock. Используйте локальный диск Ubuntu, не NFS; не запускайте несколько независимых серверов с копиями одного хранилища.

Повтор ключа проверяется до проверки занятости: повтор уже принятого запроса получает квитанцию, а не новый запуск после завершения предыдущего.

## Честная граница: не exactly-once

Между устойчивой записью квитанции и запуском процесса остаётся окно падения. После рестарта нельзя безопасно понять, успел ли процесс совершить внешнее действие. Поэтому квитанция сохраняется и блокирует повтор: возможен **потерянный запуск**, но автоматического повторения потенциально уже выполненного действия нет. Это at-most-once admission на ключ в пределах сохранённого хранилища, не exactly-once исполнения бизнес-действий. Внутренние retries плагинов также могут повторять внешние действия.

Сам плагин должен передавать idempotency key целевой системе, если нужна защита платежа/письма/записи от повторов на её стороне. Такой проброс в этой версии не добавлен. trigger_id пока идентификатор квитанции, а не run_id; API состояния квитанции нет.

## Эксплуатация

Квитанции не протухают автоматически. Это сознательно: TTL открыл бы повтор старого запроса. Следите за диском и частотой webhook на reverse proxy. Токен давайте только доверенным клиентам: валидный клиент может создавать новые ключи. Ошибка записи не разрешает запуск.

Не удаляйте `.trigger-claims` вместе со старыми логами! После удаления квитанции, смены runs_dir или отката бэкапа старый ключ снова может исполниться. Квитанции должны попадать в резервное копирование. Ручная очистка только после согласования максимального периода повторов отправителя и принятия риска.

В первой версии запись квитанций сериализована на диск — это разумно для 5–6 цепочек, не benchmark на тысячи webhook/с. Повторный запрос сам по себе новый алерт не отправляет.

## Проверки

Автоматические тесты:

1. 64 одновременных запроса с одним ключом: один 202, остальные 200, один каталог запуска, общий trigger_id.
2. Новый экземпляр fleet с прежним диском: повтор без нового запуска.
3. Занятый job: 409 не расходует ключ, повтор после освобождения принимается.
4. Невалидные ключи: 400.
5. Повреждённая квитанция: 503, без запуска.
6. Недоступное хранилище: 503, без запуска.
7. Сохранившаяся квитанция без каталога запуска: повтор не исполняется. Это моделирование неоднозначного состояния после падения, не реальный power-cut тест.

Тесты запускались с race detector, 10 повторений. Реальные отключения питания, kill -9 в каждом окне fsync и особенности диска целевого Ubuntu-сервера отдельно не проверялись.
