# Fleet: постоянная очередь, восстановление и outbox

Это реализация для одной Ubuntu-машины и локального диска. Она заменяет прежний режим «занято → пропустить» и доставку уведомлений только тремя попытками.

## 1. Очередь заданий

- Webhook сохраняет задание **до HTTP 202**. Idempotency claim и задание — одна атомарная запись состояния, без прежнего окна между отдельной квитанцией и очередью.
- При занятых слотах задание остаётся `pending`, а не теряется. Для одного job выполняется не более одного задания одновременно.
- Число одновременных запусков задаёт concurrency; предел ожидающих — `max_pending` (по умолчанию 1000, допустимо 1..100000).
- Заполненная очередь: HTTP 429 + Retry-After: 5. Повторять тот же ключ. Не принятое задание не расходует ключ.
- Расписание объединяет повторные срабатывания, если для job уже есть pending. Это намеренно не очередь на каждую минуту простоя. Webhook с разными ключами создаёт отдельные задания.
- Среди доступных job диспетчер берёт самое старое задание; занятый job не блокирует остальные.
- До запуска процесса сохраняется `running`. После завершения сохраняется итог: success/failure/timeout/cancelled.

Путь прогона: `<runs_dir>/<job>/<task_id>/`. Там output.log, result.json и штатные артефакты WEDRA.

## 2. Восстановление

После аварии:

| Состояние на диске | Поведение при старте |
|---|---|
| pending | Возобновляется ожидание и последующий запуск |
| running | interrupted + уведомление; **не перезапускается автоматически** |
| success/failure/timeout/cancelled | Не исполняется повторно |
| Повреждённый state.json | Демон отказывается стартовать |

SIGTERM отменяет начатые цепочки, записывает cancelled и сохраняет оставшиеся pending. Systemd перезапускает службу. Применяется KillMode=control-group; сам дочерний процесс также получает Linux parent-death SIGKILL. Для ручного запуска вне systemd нет обещания полного контроля произвольных отсоединившихся потомков плагина.

Контрольные точки `every` переживают рестарт; при длительном простое планируется один актуальный прогон, не все пропущенные интервалы. Cron не повторяет один и тот же текущий минутный слот после рестарта, но не воспроизводит все минуты отсутствия демона.

Удалённые из конфига job могут оставаться в очереди: задание хранит снимок настроек job на момент приёма. Pipeline и плагины при этом читаются с диска при запуске — содержимое файлов не заморожено. Перед обновлением/удалением таких файлов остановите службу и разберите очередь. Не редактируйте state.json на работающем демоне.

## 3. Постоянная очередь алертов

- Завершение задания и создание его уведомлений фиксируются одним атомарным снимком. Для timeout уведомление сохраняется сразу при срабатывании таймаута, до ожидания завершения убитого процесса.
- Telegram и HTTP-webhook имеют независимые записи и отдельных обработчиков.
- Неуспешная доставка повторяется без лимита числа попыток: 5, 10, 20… секунд, максимум 5 минут между попытками.
- Очередь и счётчики попыток переживают рестарт. Удаление одного канала из env не удаляет старые уведомления для него: они ждут восстановления настроек.
- HTTP 2xx считается подтверждением вебхука; для Telegram дополнительно проверяется JSON `ok:true`.
- На доставку — таймаут 5 секунд, перенаправления запрещены. Один неработающий канал не блокирует другой.
- Исходящий webhook содержит стабильный event_id, он же в Idempotency-Key. Получатель должен дедуплицировать его.

**Доставка at-least-once, не exactly-once:** адресат мог принять сообщение, а ответ потеряться; либо демон мог упасть до сохранения ACK. Тогда уведомление придёт повторно. Telegram не гарантирует дедупликацию по нашему event_id. В текст сообщения включён event_id для диагностики.

URL и токены НЕ пишутся в состояние: используются текущие переменные окружения при доставке. После изменения адреса/чата старые pending-уведомления будут отправлены на новый адрес/чат. Учитывайте это при смене получателя.

## 4. Проверка состояния

Оба эндпоинта требуют Authorization: Bearer, как запуск:

```bash
curl -H 'Authorization: Bearer YOUR_TOKEN' http://127.0.0.1:8770/health
curl -H 'Authorization: Bearer YOUR_TOKEN' http://127.0.0.1:8770/tasks/TASK_ID
```

Health: ok, pending, running, interrupted, undelivered_alerts, queue_limit. Ошибка дисковой записи отравляет хранилище: новые задания и диспетчеризация блокируются, health отвечает 503. Ошибки отправки при здоровом диске не дают 503 сами по себе — следите также за undelivered_alerts и журналом.

POST отвечает task_id, trigger_id (одинаковые), job, status, replayed, claimed_at. Повтор ключа даёт текущий сохранённый статус задания; это не новое исполнение. GET /tasks/<id> возвращает статус, времена и путь к артефактам, без YAML/секретов.

## 5. Хранение и пределы гарантий

Состояние: `<runs_dir>/.durable/state.json`. Временный файл 0600 → fsync файла → atomic rename → fsync каталога. Запись сериализована; очередь, idempotency claims и outbox находятся в одном снимке. Межпроцессный flock штатного fleet запрещает вторую копию на том же runs_dir.

Это не распределённая очередь и не замена PostgreSQL для большого потока. Нужен локальный Linux-файловый ресурс с корректными fsync/rename, не NFS. Атомарный снимок переписывает историю целиком; для 5–6 цепочек это просто и проверяемо, для большого/долгого потока нужен storage backend и compaction.

История задач, idempotency claims и доставленных уведомлений пока **не очищается автоматически**. Следите за диском; делайте согласованные бэкапы состояния. Удаление/откат состояния может снова разрешить старый ключ. Не удаляйте .durable при чистке output.log. Старый каталог .trigger-claims сохраняется и проверяется при обновлении: прежние ключи не запускаются заново, даже если для них нет task_id нового формата.

При полном диске нельзя гарантировать запись задания или алерта: fail-closed, CRITICAL в journal и health 503 вместо молчаливого продолжения. Уже запущенные задания могут завершиться без сохранения точного результата; после восстановления диска/рестарта будут interrupted, если running осталось на диске. Неустранимые ошибки файловой системы требуют вмешательства оператора.

Не гарантируется exactly-once бизнес-действий плагина. Ретраи внутри плагина/цепочки могут повторять внешние действия. Потерянное питание между running и реальным стартом даёт interrupted даже если процесс не успел стартовать — это намеренная осторожность.

Внешний мониторинг сервера по-прежнему нужен: выключенная машина не доставит алерт до восстановления. Встроенная модель, произвольный DAG и внешний мониторинг в этот блок не входят.

## 6. Испытания

Тесты проверяют 64 конкурентных приёма одного ключа, перезапуск с pending/running, реальный SIGKILL вспомогательного процесса, FIFO среди доступных job, ограничения очереди/параллельности, продолжение очереди новым экземпляром, атомарность результата/outbox, HTTP 503 → повтор → HTTP 204 с сохранением event_id, независимость каналов, повреждение записи, отказ диска и сохранение старых claims при обновлении.

Race-тесты повторялись. SIGKILL-проверка тестирует устойчивость состояния процесса; это не физическое отключение питания, не тест оборудования целевого сервера и не end-to-end тест реальных пользовательских плагинов/Telegram.
